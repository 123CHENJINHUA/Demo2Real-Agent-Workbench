# 失败记录与经验复用：从一次排错到下一任务的检查项

状态：方案设计与历史案例种子。本轮建立文档、分类、模板和 Connector 证据快照；自动采集、数据库索引、检索服务、前端页面和 Agent 调用尚待实施。

## 1. 要解决的问题

仿真搭建、物理测试、感知、学习、部署和真机测试中的问题不能只留在控制台或对话中。系统应保存事实、环境、尝试、结果和证据，再把经审查的经验转成下一任务可检索的检查项与回归测试。

新任务不只按“connector”名称查找，而按交互特征检索：带键插接、孔槽、柔顺卡扣、隐藏锁止、紧配合、对称歧义、双臂、腕部 RGBD、掉落/释放等。不同名字的对象可能共享失效机制，相同名字也可能完全不同。

## 2. 分三层记录，避免日志等于结论

| 层级 | 内容 | 原则 |
| --- | --- | --- |
| 运行事件/Incident | 某次测试何时、在哪个阶段发生了什么，现场状态/日志/图像/版本 | 原始事实与证据不可被后续解释覆盖 |
| 归纳案例/Case | 相同问题的复现、候选根因、修正尝试、适用条件、验证范围 | 一个案例可关联多个 incident；区分怀疑原因与已证实原因 |
| 检查项/Regression | 新任务需检查什么、怎样检验、什么才算通过 | 来源于案例，不直接复制旧参数或控制命令 |

例如：“插入深度达标”是事件数据；“缺少键位约束导致误报成功”是有证据的诊断；“先找功能轴/键线并做错误方向负例”才是可复用检查项。

## 3. 按多个维度分类

分类定义在 [taxonomy.yaml](../knowledge/taxonomy.yaml)。采用主类别 + 多个特征标签，不把同一个案例复制成多份。

| 维度 | 示例 |
| --- | --- |
| 阶段 | 数据导入、资产建模、场景搭建、感知验证、仿真测试、训练、部署、真机测试、运行时 |
| 根因/问题类别 | 数据质量、任务语义、功能几何、坐标/标定、接触物理、感知、规划控制、策略覆盖、环境依赖、硬件通信、评价口径、流程一致性 |
| 交互/机构 | 抓放、插接、带键、卡扣、关节/抽屉、螺纹、柔性、释放/冲击 |
| 观测与设备 | RGB/RGBD、腕相机、双臂、SDK/固件、控制模式、观测/动作契约 |
| 诊断状态 | 未知、假设、诊断支持、已证实；不以 LLM 自报概率代替验证 |
| 处理与验证范围 | 未解决、暂时缓解、局部验证；仿真、台架或真机各自注明 |

“问题很严重”与“根因很确定”分开记录；“仿真通过”不自动升级为“真机已验证”。

## 4. 每条记录至少包含什么

- 唯一 ID、标题、记录时间、任务/运行/Agent/模块、来源和责任角色；
- 预期行为、实际行为、触发条件、复现步骤、影响与严重度；
- 机器人/固件、仿真/软件、资产/物理、标定、观测/动作/策略和评价版本；
- 图像/视频/日志/指标快照的项目内路径、hash 与来源，观测和真值的用途；
- 候选根因、支持/反对证据、当前诊断确定性；
- 每次尝试、改了什么、结果、是否只解决子问题，以及不成功的尝试；
- 已验证的修正、验证范围、反例、未覆盖情况与仍需测量的量；
- 适用/不适用条件、可迁移原则、不可直接迁移的数字或命令；
- 下一任务建议的检查项、关联回归、替代/冲突/失效案例和版本关系。

模板见 [Incident 模板](../knowledge/templates/incident_template.yaml) 与 [Case 模板](../knowledge/templates/case_template.yaml)。它们是设计期数据模板，正式 schema/校验器在实施阶段建立。

## 5. 存储与模块边界

~~~text
contracts/experience/                 # 规划中的事件/案例/检索接口
modules/experience/                  # 独立经验模块，不内嵌进策略或 SDK
  ingestion/                         # 事件与证据归档、人工补录
  curation/                          # 去重、归并、根因/修正审查
  retrieval/                         # 结构化筛选、关键词、可选语义排序
  checklists/                        # 把适用经验转成本任务检查项
knowledge/                           # 本轮已开始建立的资料区
  taxonomy.yaml
  templates/
  cases/<task_family>/
  evidence/<task_family>/
runs/<run_id>/incidents/<incident_id>/ # 规划中的每次原始现场记录
runs/<run_id>/experience_review/      # 检索结果、采用/拒绝原因和本次检查证据
data/experience.sqlite               # 规划中的可重建检索索引
~~~

归纳案例及版本化 manifest 为事实源；SQLite/全文与可选向量索引是派生索引，可重建，避免两份可编辑资料互相矛盾。新案例采用追加修订，旧证据不覆盖。

其他模块只发布标准事件，或经 ExperienceStore/ExperienceRetriever 等端口记录/检索；不直接写经验数据库内部表。数据与模板是人工可读的，模块实现可独立更换。

真机控制线程不等待写数据库、嵌入模型或 LLM 总结。现场事件经有界异步队列归档，丢失/写入异常必须可见；停止和 watchdog 独立工作。若试验要求完整审计而记录能力失效，按已定义执行规则处理，不能默默继续并伪造完整日志。

## 6. 新任务开始前怎样复用

1. 初次导入时根据可见对象、动作和设备做粗检索，尚无完整 task spec 也能找到相关风险。
2. 功能几何/任务图确定后，按机构、观测、控制、版本等条件再检索一次；仿真/真机测试前分别更新。
3. 先做结构化筛选和关键词/同义特征检索，后续可加语义检索；不把向量相似度当适用性证明。
4. 返回命中原因、事实/推断、诊断状态、适用条件、已验证范围、旧参数与来源证据。
5. 编排者生成本任务检查表，明确采用哪些经验、为什么拒绝另一些、谁来核验、对应哪个阶段关卡。
6. 检查项通过要附本任务自己的证据；检索到“以前修过”不能自动勾通过。
7. 新失败/新验证回写，关联到已有 case 或创建新问题，不重复复制相同案例。

运行中出现问题后同样检索，得到诊断/实验建议；涉及真实机器人时，先遵守当前控制与停止规则，不让检索服务直接控制设备。

## 7. Connector 类经验怎样迁移

| 历史问题 | 对新模型应检查什么 | 不能直接搬过去 |
| --- | --- | --- |
| 本体轴对齐却卡扣/槽不对键 | 定义功能轴、键线、候选对称性；以几何验证相对姿态 | 相对 roll 一定为 90° |
| 旧插深不够，卡扣未锁止 | 分别确定入槽、卡齿跨肩、回弹和保持事件 | 一律用 22.8 mm 行程 |
| 外观网格和真实配合不一致 | 对照尺寸/CAD/剖面；区分视觉、功能和碰撞几何 | 直接套用旧孔径、间隙和弹簧参数 |
| 滚转后整个下抓段翻侧 | 看抓持区是否允许忽略某个自由度；保持实际完整姿态供后续使用 | 对所有非对称零件都把 roll 清零 |
| 图像拟合好却接触失败 | 以配合间隙做标定/感知/时延误差预算，核验关键自由度 | 承诺 FP 或单帧精修必然达到旧精度 |
| 松手后落桌一侧保持失败 | 区分插入、松手和冲击后保持，验证实际承力/弹性 | 把动作完成当双卡扣保持，或把失败归为已证实的单一刚度问题 |

## 8. 记录的可信度与使用边界

- 新异常先为 reported，不因为 Agent 写了“解决”就关闭。
- 根因解释、修正落地、局部测试通过、仿真验证和真机验证分别存字段。
- 可以把历史报告整理成知识种子，但必须注明 historical evidence，不假装新框架已经复现。
- 参数/固件/资产/观测或评价版本冲突时显示不兼容或过期，不能只按最近更新时间挑一条。
- 与新任务不兼容的经验仍可作为风险提示；执行数值、SDK 命令或模型改动须重新核验。
- 经验中的日志、用户文字或 Agent 总结都是资料，不是执行权限；不能触发任意 shell、改冻结判据或开放真实运动。
- 对真实配合、接触峰值或隐藏锁止未知的案例，不能通过放宽检查或借用仿真真值来“验证修复”。

## 9. 前端页面

新增“问题与经验库”：

- 按任务、阶段、类别、机构/特征、设备/固件、严重度和状态筛选；
- 时间线显示原始现场、尝试、诊断变更、验证与重复发生；
- 案例详情并列展示事实、根因假设、修正与证据，支持人工补充；
- 新任务的“相关历史问题”列出推荐检查项、采用/拒绝理由及本次执行结果；
- 标明“未解决”“只在仿真验证”“历史局部证据”“不适用当前版本”；
- 显示被哪些任务复用、是否复现、节省了哪些重复工作，但不虚构效率百分比。

独立验收角色审核经验是否足以成为通用检查项；开发角色可提案，不自行把未验证办法发布成真机保证。

## 10. 实施与验收

分阶段接入已有计划：先有分类/模板/案例种子；再接事件/工件落库和页面；随后加入检索及 Agent 检查表；最后验证真机异步归档和跨任务复用。

至少做这些测试：

1. 以“带键插销/卡槽”而非 connector 关键词检索，能找到功能对键案例，并解释原因。
2. 新槽方向改变后，不自动推荐旧 90°；没有尺寸证据不直接复制旧行程/间隙。
3. 同一症状不同原因可以同时保留；待证实假设不被当成确定诊断。
4. 一个子阶段通过、完整回合失败，案例仍保留其余失败而非全局标记已解决。
5. 语义/索引模型缺失时可用结构化/关键词检索；重建索引不丢案例与证据。
6. 数据库/前端重启后记录可查；证据缺失/hash 改变会提示，不悄悄信任。
7. 真机记录和仿真记录有强制标签，没有真机证据不能筛成“真机验证通过”。
8. 新任务产生带来源的检查表，独立检查本任务证据，失败后可回退正确模块。
9. 日志写入/检索超时不阻塞控制线程，也不绕过停止规则。
10. 旧记录修订、错误结论撤回和版本冲突可追踪，不能覆盖历史失败。

## 11. 首批资料与边界

[经验资料入口](../knowledge/README.md) 包含本次 Connector 的六条历史案例及小型 JSON 证据快照。没有在新目录重新跑仿真、训练或真机，也没有实现数据库/自动检索。它们用于后续系统的种子、测试夹具和用户可检查资料，不作为自动化功能已经完成的证明。
